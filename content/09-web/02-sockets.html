Ya sabes abrir una conexión y enviar bytes. Ahora el cliente envía dos mensajes seguidos: uno y dos. ¿Cómo sabe el servidor dónde acaba el primero y dónde empieza el segundo?

El concepto

No lo sabe. TCP no conoce los mensajes: es un flujo de bytes, como el agua de un grifo. Lo que escribes en dos veces puede llegar en un solo Read, y lo que escribes de golpe puede llegar en dos.

Por eso los dos programas acuerdan un protocolo: unas reglas sobre qué se envía. La más sencilla es que cada mensaje sea una línea acabada en \n. bufio.Scanner lee justo hasta ahí.

Bytes, no mensajes

Animación: el cliente escribe uno\n y luego dos\n, y dentro de la conexión queda una sola fila de bytes. Un Read se lleva un trozo cualquiera, uno\nd. Scan, en cambio, corta en cada \n y devuelve uno y después dos.

Un error a propósito

Leer con Read y suponer que cada lectura es un mensaje:

func handle(conn net.Conn) {
	defer conn.Close()
	buf := make([]byte, 1024)
	for {
		n, err := conn.Read(buf)
		if err != nil {
			return
		}
		fmt.Printf("mensaje: %q\n", buf[:n])
	}
}
mensaje: "uno\ndos\n"

Cómo leer el error

mensaje: "uno\ndos\n"

Aquí no hay mensaje de error: el fallo es silencioso. El cliente envió dos líneas con printf 'uno\ndos\n' | nc -N localhost 8080, y un solo Read se las llevó juntas. Otras veces llegarían partidas. Read devuelve los bytes que ya han llegado, sin saber de mensajes. Para leer mensajes, usa un Scanner.

El error típico

Olvidar el \n al responder:

fmt.Fprint(conn, strings.ToUpper(sc.Text())) // sin \n

El cliente lee con Scan, que espera hasta encontrar un \n. Como nunca llega, se queda esperando. Si tu protocolo dice que cada mensaje acaba en \n, los dos lados tienen que cumplirlo: usa Fprintln.
