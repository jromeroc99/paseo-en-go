Quien recibe de un canal no sabe cuántos valores le van a llegar. Si sigue esperando cuando ya no queda nada, el programa se bloquea. Le falta una señal que diga: «ya está, no hay más».

El concepto

close(ch) cierra un canal: avisa de que no se enviarán más valores. Los que ya estaban dentro se pueden seguir recibiendo.

for v := range ch recibe los valores uno a uno hasta que el canal está cerrado y vacío; entonces el bucle termina.

Para saber si un canal está cerrado, recibe con dos variables: v, ok := <-ch. ok es false cuando el canal está cerrado y ya no quedan valores.

Cerrar el canal

Animación: range ch espera. La goroutine envía 1 y 2, y el bucle los imprime. Después hace close(ch). El canal está cerrado y vacío, así que range termina y main sigue.

Un error a propósito

Borra close(ch) de countdown en el ejemplo y ejecútalo: 

3
2
1
fatal error: all goroutines are asleep - deadlock!

goroutine 1 [chan receive]:
main.main()
	.../main.go:14 +0xc5
exit status 2

Cómo leer el error

goroutine 1 [chan receive]:
main.main()
	.../main.go:14 +0xc5

Imprime 3, 2 y 1, y luego se bloquea. chan receive: main estaba recibiendo en la línea 14, la del range. countdown ya había terminado sin cerrar el canal, así que range esperaba un cuarto valor que nunca iba a llegar.

El error típico

Cerrar el canal y seguir enviando: 

package main

import "fmt"

func main() {
	ch := make(chan int, 1)
	close(ch)
	ch <- 1
	fmt.Println(<-ch)
}

Solo cierra quien envía

panic: send on closed channel

goroutine 1 [running]:
main.main()
	.../main.go:8 +0x45
exit status 2

«Enviar por un canal cerrado» no es un bloqueo: es un panic, y el programa se para en la línea 8. Por eso solo cierra quien envía, y solo cuando ya no va a enviar más. Quien recibe nunca cierra.

No hace falta cerrar todos los canales: cierra solo cuando quien recibe necesita saber que se ha acabado, como con range.
